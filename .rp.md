# WordPress Studio conventions

## Issues

Issues are the Studio team's own: Linear issues of the team "Studio App & CLI" (`STU`), read through the Linear MCP, and GitHub issues of `Automattic/studio`, read with `gh`. Pipelines only read them: never create, modify, label, or comment on an issue. Pipelines reference an issue by its Linear identifier, such as `STU-123`, or GitHub identifier, such as `Automattic/studio#123`.

## Pipeline slug

`<Linear identifier, lowercased>-<short kebab-case description>`, such as `stu-123-fix-sync-retry`; for a GitHub issue, `gh-<number>-<short kebab-case description>`.

## Pipeline branch format

`rp/<pipeline slug>`, so the local pipeline branch never takes the upstream branch's name.

## Artifact storage

`artifacts-in-fork`, without a fork remote.

- Upstream: the remote `origin`, `https://github.com/Automattic/studio.git`.
- The artifact base branch is `radical-pipelines`: `trunk` plus the commits adding `.rp.md` and the `.worktrees/` entry in `.gitignore`, checked out in the main checkout. It is the only artifact branch on `origin`. To update it before a pipeline starts, run `git fetch origin`, fast-forward it to `origin/radical-pipelines`, merge `origin/trunk` into it, and push it to `origin`.
- Pipeline and lane branches, with their `.pipelines/` folders, stay local: never push them.
- Upstream pull requests follow the upstream PR transformation: a clean branch from `origin/trunk` with the net change, pushed to `origin` only once the owner approves opening the pull request.
- Upstream branch: the pipeline slug, such as `stu-123-fix-sync-retry`; the owner confirms it.
- Upstream commits: one line, clear and descriptive, saying what changed and why, without agent attribution.

## Worktree folder root

`.worktrees`

## Pipelines folder root

`.pipelines`

## Commit format

`<imperative description> ({profile})`: one clear, descriptive line, focused on what and why.
The orchestrator's commits end with `(orchestrator)`, and a commit a person makes with an agent outside a pipeline with `(assisted)`.

## PR format

Follow `.github/PULL_REQUEST_TEMPLATE.md`. In Proposed Changes, describe the intent of the change and its user impact, not the modified files or implementation mechanics. The title is one clear, descriptive line, like the subjects of recent `trunk` commits. End Proposed Changes with the places in the change most worth a reader's attention.

- Title: `Description`.
- Description: `.github/PULL_REQUEST_TEMPLATE.md`. Its "How AI was used in this PR" section reads `100% of the code, tests, and comments in this PR were autonomously generated by AI and reviewed by {@github_handle} before the PR was opened.`, with the owner's GitHub handle.

## Lanes

- spec-producer:
    - `focused`: Change only what the intent requires: no unrelated refactor, and no change to existing behavior the intent does not ask for. Require, design, and build only what the intent asks for or a use the code at `{merge-base}` already has needs. What only a later change, an unmerged change, or a use nobody has yet would need stays out. Record whatever these rules keep out that the work would otherwise have included: what it is, what it would give, and why it stays out. Record it in one section of your artifact, or of your review, so a reader finds every such item in one place.
    - Consolidation: Change only what the intent requires: no unrelated refactor, and no change to existing behavior the intent does not ask for. Require, design, and build only what the intent asks for or a use the code at `{merge-base}` already has needs. What only a later change, an unmerged change, or a use nobody has yet would need stays out. Record whatever these rules keep out that the work would otherwise have included: what it is, what it would give, and why it stays out. Record it in one section of your artifact, or of your review, so a reader finds every such item in one place.
- design-doc-producer:
    - `direct`.
    - `simpler`, after `direct`: Design an approach that satisfies the spec with less than the previous candidates: fewer new concepts, layers, and indirections, and less for a reader new to the code to learn.
    - Consolidation: Take the candidate a reader new to the code follows with the least to learn. Take a part of another candidate where the spec fails without it, or where it brings the change closer to the intent's goal within the guardrails.
- reviewer: one lane per reviewer row in **Models**, named after its model, without a brief.

## Guardrails

### lint

- profiles: implementer

Run oxlint with `--fix` and Prettier with `--write` on every JavaScript and TypeScript file outside `.pipelines/` that the change adds or modifies since `{merge-base}`, and ESLint with `--fix` on every CSS file it adds or modifies there, committed or not, and confirm they report no errors. ESLint checks only stylesheets; oxlint checks the code. Never lint or format the whole repository:

```sh
changed() { git diff --name-only --diff-filter=d {merge-base} -- "$@" ':!.pipelines'; git ls-files --others --exclude-standard -- "$@" ':!.pipelines'; }
changed '*.js' '*.mjs' '*.cjs' '*.jsx' '*.ts' '*.mts' '*.cts' '*.tsx' | xargs -r npx oxlint --fix
changed '*.js' '*.mjs' '*.cjs' '*.jsx' '*.ts' '*.mts' '*.cts' '*.tsx' | xargs -r npx prettier --write
changed '*.css' | xargs -r npx eslint --fix
```

### lint-review

- profiles: reviewer

Run oxlint and Prettier with `--check`, without fixing anything, on every JavaScript and TypeScript file outside `.pipelines/` that the change adds or modifies since `{merge-base}`, and ESLint, without `--fix`, on every CSS file it adds or modifies there, committed or not, and confirm they report no errors. ESLint checks only stylesheets; oxlint checks the code. Never lint or format the whole repository:

```sh
changed() { git diff --name-only --diff-filter=d {merge-base} -- "$@" ':!.pipelines'; git ls-files --others --exclude-standard -- "$@" ':!.pipelines'; }
changed '*.js' '*.mjs' '*.cjs' '*.jsx' '*.ts' '*.mts' '*.cts' '*.tsx' | xargs -r npx oxlint
changed '*.js' '*.mjs' '*.cjs' '*.jsx' '*.ts' '*.mts' '*.cts' '*.tsx' | xargs -r npx prettier --check
changed '*.css' | xargs -r npx eslint
```

### typecheck

- profiles: implementer, reviewer

Run `npm run typecheck` and confirm it passes.

### tests

- profiles: implementer, reviewer

Run the tests relevant to the change with `node .pipelines/bin/env.mjs test unit <paths> --agent {agent}` (every test file the change adds or modifies, and the tests of the modules it changes) and confirm they pass. Never run `npm test` directly: it also runs the CLI e2e tests, outside your own Studio.

### cli-e2e-filtered

- profiles: implementer

When the change alters the CLI or code it runs (`apps/cli`, `packages/`), run the CLI e2e files that cover it with `node .pipelines/bin/env.mjs test cli-e2e <files> --agent {agent}`. They must pass.

### cli-e2e-whole

- profiles: reviewer

When the change alters the CLI or code it runs (`apps/cli`, `packages/`), run every CLI e2e file once with `node .pipelines/bin/env.mjs test cli-e2e --agent {agent}`. It must pass.

### e2e-filtered

- profiles: implementer

When the change alters what the desktop app does (`apps/studio`, `apps/ui`, `apps/cli`, `packages/`), run the specs under `apps/studio/e2e/` that cover it with `node .pipelines/bin/env.mjs test e2e <spec paths> --agent {agent}`. They must pass.

### e2e-whole

- profiles: reviewer

When the change alters what the desktop app does (`apps/studio`, `apps/ui`, `apps/cli`, `packages/`), run the whole suite once with `node .pipelines/bin/env.mjs test e2e --agent {agent}`. It must pass.

### knip

- profiles: implementer, reviewer

Run `npm run knip` and confirm it reports nothing.

### light-and-dark

- profiles: implementer, reviewer

When the change affects UI or CSS, verify the result in a running app in both the light and the dark color scheme, and record what was checked in each.

### agent-evals

- profiles: implementer, reviewer

When the change touches the Studio Code system prompt, a tool's definition, description, or result shape, or an agent skill or instruction, update the affected assertions in `scripts/eval/promptfoo.config.yaml` and run the affected cases with `node .pipelines/bin/env.mjs eval --filter-pattern "<case>" --agent {agent}`. When the command reports that your Studio has no login, say so and flag the cases for a human eval run instead of skipping them silently.

### agents-md

- profiles: design-doc-producer, implementer, reviewer

Follow `AGENTS.md` and the READMEs and design docs it points to for the areas the change touches, including its Common Pitfalls and its rule on code comments.

### scope

- profiles: spec-producer, design-doc-producer, implementer, reviewer

Change only what the intent requires: no unrelated refactor, and no change to existing behavior the intent does not ask for.

### present-need

- profiles: spec-producer, design-doc-producer, implementer, reviewer

Require, design, and build only what the intent asks for or a use the code at `{merge-base}` already has needs. What only a later change, an unmerged change, or a use nobody has yet would need stays out.

### least-machinery

- profiles: design-doc-producer, implementer, reviewer

Of the approaches that satisfy the spec, take the one a reader new to the code follows with the least to learn: the fewest new concepts, layers, and indirections.

- Prefer code written out and read in place to code discovered, generated, or inferred.
- Prefer a check whose failure reads plainly to a guarantee whose failure the reader must decode, whatever stage each runs at.
- Add no dependency on a tool, a build step, or a runtime the code does not already depend on.
- Keep repetition between sibling modules when removing it adds a concept. `AGENTS.md`'s rules on single implementations still bind.

### test-value

- profiles: design-doc-producer, implementer, reviewer

Plan and write a test for a behavior a user or a caller can observe and that can break. Write none for how the code is built, or for a behavior another test covers. Follow the testing conventions `AGENTS.md` points to for the area.

### left-out

- profiles: spec-producer, design-doc-producer, implementer, reviewer

Record whatever these guardrails keep out that the work would otherwise have included: what it is, what it would give, and why it stays out. Record it in one section of your artifact, or of your review, so a reader finds every such item in one place.

## Resources

### studio-cli

- profiles: implementer, reviewer

The `studio` CLI from this worktree, with a Studio of your own that shares nothing with the owner's or another agent's: its own home, config, daemon, sites, ports, and temp files. Run it only as `node .pipelines/bin/env.mjs studio --agent {agent} -- <command>` from the worktree root, never as `node apps/cli/dist/cli/main.mjs` or through the `cli:*` scripts: the script builds the CLI first when the code changed since, taking turns with the worktree's other agents, and runs it with your environment. A relative `--path` is a site in your own sites folder. Nothing it runs opens a window: browser, Finder, and editor calls are logged instead. Deleting a site with its files deletes them for good. Requests for the owner's password are refused, so never give a site a custom domain or HTTPS. Your daemon and sites stop by themselves after 30 minutes without use, keeping their data, and the next command starts them again. `node .pipelines/bin/env.mjs status` shows what the worktree's agents run.

### studio-servers

- profiles: implementer, reviewer

Three browser apps of this worktree, each started with `node .pipelines/bin/env.mjs <app> up --agent {agent}`, which builds what it needs, starts it on a port of your own, and prints its URL; later calls print it again at once:

- `ui`: the `studio ui` app, serving `apps/ui` and `apps/local` with your own Studio. Dismiss the welcome tour.
- `web`: Studio on the web, `apps/ui` over its `static` connector, with sites in WordPress Playground.
- `playground`: real `apps/ui` components with sample data and no backend, in light and dark (`apps/ui/src/dev/README.md`).

Open them with a browser tool. The apps follow the system color scheme: emulate `prefers-color-scheme` to check light and dark. Each stops after 30 minutes without use, and `up` starts it again; `node .pipelines/bin/env.mjs down <app> --agent {agent}` stops it.

### cli-e2e

- profiles: implementer, reviewer

The CLI e2e tests (`*.e2e.test.ts` under `apps/cli`), run with your own Studio, one file at a time: `node .pipelines/bin/env.mjs test cli-e2e [<files>] --agent {agent}`, every file when none is given.

### desktop-e2e

- profiles: implementer, reviewer

The desktop app's Playwright suite (`apps/studio/e2e/`), run in a Linux container so nothing opens on the owner's screen: `node .pipelines/bin/env.mjs test e2e [<spec paths>] --agent {agent}`, the whole suite when no path is given (about 4 minutes). The first run in a worktree installs and packages the app in the container (about 3 minutes); later runs package it again only when code outside `apps/studio/e2e/`, `playwright.config.ts`, and `test-fixtures/` changed (about 25 seconds). Results, traces, and daemon logs go to `test-results/` at the worktree root, replaced by each run. Runs in a worktree take turns, and the machine runs at most two at once: a run may wait, says what it waits for, and starts by itself; let it wait. Never run `npm run e2e` or Playwright on the host. The container runs Linux, so what only macOS has, such as Spotlight, signing, the app menu, and the keychain, stays untested: say so when the change touches it.

### evals

- profiles: implementer, reviewer

The Studio Code eval suite (`scripts/eval/README.md`): `node .pipelines/bin/env.mjs eval --filter-pattern "<case>" --agent {agent}` builds the CLI in its turn and runs the cases. It needs a WordPress.com login in your Studio, and consumes AI credits; without a login the command says so. Run only the affected cases, one run at a time; the full suite (~25 minutes) only when the change touches the system prompt.

## Lifecycle hooks

`env.mjs` below stands for `node .pipelines/bin/env.mjs`, run from the root of the worktree named. It gives each agent a Studio of its own (see **Resources**): the agents' commands start what they need, and everything stops by itself when idle, keeping its data. Your part is to stop and delete them.

### after-creating-worktree

- **Blocking:** run `env.mjs install`. It installs the dependencies with `npm ci`, retrying network errors itself.

### run-ended

- Run `env.mjs down all` in the pipeline worktree: it stops everything the worktree runs, keeping its data for the next run.
- When the run ended with the pipeline complete through its target phase, spawn one subagent in the main checkout with the prompt below, its placeholders filled, `<commit>` with the pipeline branch's tip and `<merge-base>` with that tip's merge-base with the base branch, both as full hashes, on the model **Models** maps the name `opus` to for the active tool. It is a plain subagent, not a role: it gets no assignment. It reads the pipeline at that commit, so removing the pipeline's worktrees or adding commits to its branch while it works changes nothing it reads. Give the owner its answer verbatim in your final report. When the owner asks for more detail about an item, or wants one recorded as later input, you can ask the subagent for input.

  > List the follow-ups this pipeline leaves. Change no file.
  >
  > Read everything at commit `<commit>`, never from a working tree: `git show <commit>:<path>` for a file, `git ls-tree -r --name-only <commit> -- <path>` for a folder. Read `<pipeline folder>`, its path relative to the repository root: `0-intent/`, the spec, the design doc, the lane candidates of both, `3-implementation/notes.md`, and every thread in `threads/`, whichever of them exist. When the code changed, read the change: `git diff <merge-base> <commit>`, without `<pipelines folder root>`.
  >
  > List what the pipeline's roles found and left out. Do not review the artifacts or the change again. When the code changed, check each item against the code at `<commit>`: what the change already handles is no item.
  >
  > Sections, in this order, each omitted when empty:
  >
  > - **Left out for now**: requirements, cases, guarantees, generalizations, and tests a role kept out because nothing needs them yet, with what each would give.
  > - **Behavior changes set aside**: changes to existing behavior a role saw reason for and the intent did not ask for.
  > - **Approaches not taken**: what a candidate or a thread proposed and the pipeline left, when it gives something the chosen approach does not.
  > - **Deferred**: work an artifact or a thread leaves for later, naming where it is recorded, or that it is recorded nowhere.
  > - **Edge cases**: inputs or states a user can reach that the change is known not to handle.
  > - **Bugs found, not fixed**: defects the roles came across outside the change's scope.
  > - **Narrow fixes**: a defect the change fixes in its own case; search for the same pattern elsewhere and name where it remains.
  > - **Suggestions**: changes an approval suggests without requiring.
  > - **Unverified**: what a role says it could not test or run.
  > - **Debt**: shortcuts the change itself introduces.
  >
  > Leave out what the pipeline says no use reaches. Make one item of items that share a cause. Number the items across sections. Write each in as few words as explain it to someone who has not read the pipeline, name the thread or artifact that says so, and say whether it stands as a change of its own. I may ask you for more about any item later. No introduction, no summary, nothing about what went well. With no items, answer `Nothing left behind.`

### before-removing-worktree

- Run `env.mjs down all --remove`, then `env.mjs prune`, in the worktree: the first deletes everything the worktree runs, with its data, and the second whatever worktrees that no longer exist left on this machine.
