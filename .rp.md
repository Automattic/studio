# WordPress Studio conventions

## Issues

Issues are the Studio team's own: Linear issues of the team "Studio App & CLI" (`STU`), read through the Linear MCP (`get_issue`, `list_comments`), and GitHub issues of `Automattic/studio`, read with `gh issue view <number> --comments`. Pipelines only read them: never create, modify, label, or comment on an issue. Work without an issue does not start a pipeline: ask the owner for one. Pipelines reference an issue by its Linear identifier, such as `STU-123`, or as `Automattic/studio#123`.

## Pipeline slug

`<Linear identifier, lowercased>-<short kebab-case description>`, such as `stu-123-fix-sync-retry`; for a GitHub issue, `gh-<number>-<short kebab-case description>`.

## Pipeline branch format

`rp/<pipeline slug>`, so the local pipeline branch never takes the upstream branch's name.

## Artifact storage

`artifacts-in-fork`, without a fork remote.

- Upstream: the remote `origin`, `https://github.com/Automattic/studio.git`.
- The artifact base branch is `radical-pipelines`: `trunk` plus the commit adding `.rp.md` and the `.worktrees/` entry in `.gitignore`, checked out in the main checkout. It is the only artifact branch on `origin`. To update it before a pipeline starts, run `git fetch origin`, fast-forward it to `origin/radical-pipelines`, merge `origin/trunk` into it, and push it to `origin`.
- Pipeline and lane branches, with their `.pipelines/` folders, stay local: never push them.
- Upstream pull requests follow the upstream PR transformation: a clean branch from `origin/trunk` with the net change, pushed to `origin` only once the owner approves opening the pull request.
- Upstream branch: the pipeline slug, such as `stu-123-fix-sync-retry`; the owner confirms it.
- Upstream commits: one line, clear and descriptive, saying what changed and why, without agent attribution.

## Worktree folder root

`.worktrees`

## Pipelines folder root

`.pipelines`

## Commit format

`<imperative description> ({profile})`: one clear, descriptive line, focused on what and why. The orchestrator's commits end with `(orchestrator)`.

## PR format

Follow `.github/PULL_REQUEST_TEMPLATE.md`: Related issues, How AI was used in this PR, Proposed Changes, Testing Instructions, Pre-merge Checklist. In Proposed Changes, describe the intent of the change and its user impact, not the modified files or implementation mechanics. The title is one clear, descriptive line, like the subjects of recent `trunk` commits.

## Lanes

- spec-producer:
    - `demands`: Read the intent for what it demands: every outcome it asks for, and each input intended use produces that an outcome must handle.
    - `omits`: Read the intent for what it leaves out: the cases, mechanisms, and guarantees it does not ask for and no intended use produces, and keep the spec to what remains.
- reviewer: one lane per reviewer row in **Models**, named after its model, without a brief.

## Guardrails

### lint

- profiles: implementer, reviewer

Run ESLint with `--fix` on every JavaScript and TypeScript file outside `.pipelines/` that the change adds or modifies since `{merge-base}`, committed or not, and confirm it reports no errors:

```sh
{ git diff --name-only --diff-filter=d {merge-base} -- '*.js' '*.mjs' '*.cjs' '*.jsx' '*.ts' '*.mts' '*.cts' '*.tsx' ':!.pipelines'; git ls-files --others --exclude-standard -- '*.js' '*.mjs' '*.cjs' '*.jsx' '*.ts' '*.mts' '*.cts' '*.tsx' ':!.pipelines'; } | xargs -r npx eslint --fix
```

The reviewer runs it without `--fix`. Never lint the whole repository.

### typecheck

- profiles: implementer, reviewer

Run `npm run typecheck` and confirm it passes.

### tests

- profiles: implementer, reviewer

Run the tests relevant to the change with `npm test -- <paths>` (every test file the change adds or modifies, and the tests of the modules it changes) and confirm they pass.

### knip

- profiles: implementer, reviewer

Run `npm run knip` and confirm it reports nothing.

### light-and-dark

- profiles: implementer, reviewer

When the change affects UI or CSS, verify the result in a running app in both the light and the dark color scheme, and record what was checked in each.

### agent-evals

- profiles: implementer, reviewer

When the change touches the Studio Code system prompt, a tool's definition, description, or result shape, or an agent skill or instruction, update the affected assertions in `scripts/eval/promptfoo.config.yaml` and run the affected cases with `npm run eval -- --filter-pattern "<case>"`. When `studio auth login` is unavailable, say so and flag the cases for a human eval run instead of skipping them silently.

### agents-md

- profiles: design-doc-producer, implementer, reviewer

Follow `AGENTS.md` and the READMEs and design docs it points to for the areas the change touches, including its Common Pitfalls and its rule on code comments.

### scope

- profiles: implementer, reviewer

Touch only the files the change requires; no unrelated refactors.

## Resources

### studio-ui

- profiles: implementer, reviewer

The `studio ui` browser app, serving this worktree's `apps/ui` and `apps/local`. From `{worktree}`, build it with `npm run cli:build:ui` (plain `cli:build` does not rebuild the UI), then start it with `DEV_CONFIG_DIR={studio-home} STUDIO_PROCESS_MANAGER_HOME={studio-home}/daemon node apps/cli/dist/cli/main.mjs ui --no-open --port <free port>`. The two variables keep it off the owner's `~/.studio` config and daemon; never start it without both. Port 8081 is the default and may be taken. Open `http://localhost:<port>` with a browser tool and dismiss the welcome tour; the app follows the system color scheme, so emulate `prefers-color-scheme` to check light and dark. Sites created from the app go to `~/Studio/`: name them starting with `{pipeline-slug}-` and delete each one you create. Before ending your turn, stop the server and run `site stop --all` as in `studio-cli`.

### studio-cli

- profiles: implementer, reviewer

The `studio` CLI from this worktree. Build it with `npm run cli:build`, then run `DEV_CONFIG_DIR={studio-home} STUDIO_PROCESS_MANAGER_HOME={studio-home}/daemon node apps/cli/dist/cli/main.mjs <command>` from `{worktree}`, never without both variables, which keep it off the owner's `~/.studio` config and daemon. `--path` defaults to the current folder, so give every site command one: create sites with `site create --path {studio-home}/sites/<name> --skip-browser`, and delete them with `site delete <path> --no-files`. Before ending your turn, run `site stop --all`, which stops your own daemon and its sites.

### ui-playground

- profiles: implementer, reviewer

`BROWSER=none npm -w @studio/ui run playground` renders real `apps/ui` components with sample data and no backend, in light and dark (`apps/ui/src/dev/README.md`); `BROWSER=none` keeps its `--open` from opening a browser. It serves on port 5300, or the next free port, which Vite prints. Stop it before ending your turn.

### studio-web

- profiles: implementer, reviewer

Studio on the web: `npm -w @studio/ui run dev:static` serves `apps/ui` over its `static` connector, with sites in WordPress Playground, on port 3456 or the next free port, which Vite prints. Stop it before ending your turn.

### evals

- profiles: implementer, reviewer

The Studio Code eval suite (`scripts/eval/README.md`): `npm run eval -- --filter-pattern "<case>"`, results with `npm run eval:view`. It needs `studio auth login` and consumes AI credits; each case uses its own temporary sites root. Run only the affected cases, one run at a time; the full suite (~25 minutes) only when the change touches the system prompt.

## Lifecycle hooks

### after-creating-worktree

- **Blocking:** run `npm ci --no-audit --no-fund` from the worktree root. Its postinstall downloads sometimes fail on a network error, such as `ECONNRESET` or `ETIMEDOUT`: on such a failure, run it again, up to three attempts in all.

## Variables

- `studio-home`: `/tmp/studio-{pipeline-slug}-{role}`

## Health monitoring

Interval: 50 minutes. Stall threshold: 30 minutes.
